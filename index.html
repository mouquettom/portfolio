OpenClassrooms project

Epic Events — secure CRM back-end

A command-line CRM for a fictional event company: clients, contracts and events, shared by three departments (management, sales, support) with different access rights.

  • 481 tests
  • 95% coverage
  • 3 roles

What I built

  • A layered architecture: controllers (console interface), services (business rules and permissions), repositories (SQLAlchemy queries) and models.
  • Email and password authentication: bcrypt hashing and an HS256-signed JWT that expires after 60 minutes.
  • Role-based permissions enforced in the service layer, independently of the menus shown.
  • The business rules from the specification: an event can only exist for a signed contract, the amount due can be neither negative nor higher than the total, an employee cannot delete their own account.

Technical highlights

  • PostgreSQL schema versioned with Alembic migrations.
  • Sentry monitoring: business errors are shown to the user, only unexpected errors are reported, without personal data.
  • Unit, integration and functional tests with pytest and test-data factories.

Next steps

  • Expose the business logic through a REST API.
  • Run the test suite automatically in continuous integration.

Python · SQLAlchemy 2 · PostgreSQL · Alembic · PyJWT · bcrypt · Sentry · Pytest

OpenClassrooms project

SoftDesk API — secure REST API

The API of a B2B issue-tracking application: users create projects, add contributors, open issues and comment on them. 

POST  /api/token/access/
GET   /api/projects/
POST  /api/projects/{id}/contributors/
GET   /api/projects/{id}/issues/
POST  /api/projects/{id}/issues/{id}/comments/

What I built

  • A REST API with Django REST Framework and nested routes: projects, then issues, then comments.
  • JWT authentication (Simple JWT): 30-minute access tokens, one-day refresh tokens.
  • Three custom permissions: only contributors can access a project, only the author can edit or delete their content, only a project's author can manage its contributors.

Technical highlights

  • A custom user model designed with GDPR in mind: minimum age of 15, explicit consent (to be contacted, to share data), account deletion by the user.
  • Separate serializers for public and personal profiles: the API never exposes another user's email or age.
  • An issue can only be assigned to a project contributor; write-only hashed passwords; UUIDs for comments; pagination by 20.

Next steps

  • Cover the permissions with an automated test suite.

Python · Django · Django REST Framework · Simple JWT · drf-nested-routers · SQLite

OpenClassrooms project

LIT-Revu — Django web application

A community platform for book and article reviews: members request a review by posting a ticket, others answer it, and everyone follows the people they are interested in.

What I built

  • Sign-up and login; creating and editing tickets (with an image) and reviews, or both in a single step.
  • A follow system and a personalised feed that mixes the tickets and reviews of followed users, sorted by date.
  • User search with JavaScript autocomplete.

Technical highlights

  • Database uniqueness constraints: one review per user and per ticket, no duplicate follows.
  • Feed queries optimised with select_related to avoid N+1 queries, and an index on the creation date.
  • The image file is deleted along with its ticket.

Next steps

  • Add automated tests for the feed and for edit permissions.

OpenClassrooms project

AlgoInvest & Trade — constrained optimisation

Finding the best combination of shares to buy with a €500 budget: a variant of the knapsack problem, on 20 shares and then on two datasets of 1,000 shares.

Comparison of the two algorithms
Brute force Greedy algorithm
Complexity O(2ⁿ) O(n log n)
20 shares 1,048,576 combinations tested, €99.08 profit (optimal) €97.48 profit, in a few milliseconds
1,000 shares Impossible: 2¹⁰⁰⁰ combinations Close to €198 profit on each dataset

What I built

  • A brute-force search over all 2²⁰ combinations using bitmasks, giving the optimal reference solution.
  • A greedy algorithm that sorts shares by return, then buys them while the budget allows.
  • Data cleaning (zero or negative prices) and a report comparing my results with the analyst's.

Next steps

  • Compare the greedy algorithm with an exact dynamic-programming solution to measure the gap to the optimum.

Python · pandas · Algorithms · Complexity

Personal project · in production

Contact API — FastAPI in production

This site's contact form relies on an API I built and deployed: it validates every message, then forwards it to me by email.

  1. Formthis site
  2. FastAPIapi.tommouquet.com
  3. Resendsends the email
  4. My inboxwith “reply-to”

What I built

  • A POST /contact endpoint in FastAPI with Pydantic validation: valid email, minimum and maximum lengths, surrounding whitespace stripped.
  • Asynchronous email delivery through the Resend API, with the sender's address set as “reply-to”.
  • A static front end kept separate from the API, with a Docker image (Nginx) built and checked on every push.

Technical highlights

  • Security: content escaped before going into the HTML email, line breaks stripped from the subject, CORS restricted to my domains and to POST.
  • Configuration through environment variables, failing fast at startup when a key is missing, plus a /health endpoint.
  • GitHub Actions pipeline: Pytest and Playwright tests, Docker image build, then deployment of the site to Render, only if everything passes.

Next steps

  • Test the API itself with FastAPI's TestClient and a mocked email service.
  • Add spam protection: a honeypot field and rate limiting.

Python · FastAPI · Pydantic · Resend · Docker · Nginx · GitHub Actions · Playwright · Render
