Projet OpenClassrooms

Epic Events — CRM back-end sécurisé

Un CRM en ligne de commande pour une entreprise d'événementiel fictive : clients, contrats et événements, partagés entre trois départements (gestion, commercial, support) qui n'ont pas les mêmes droits.

  • 481 tests
  • 95 % de couverture
  • 3 rôles

Ce que j'ai construit

  • Une architecture en couches : contrôleurs (interface console), services (règles métier et permissions), repositories (requêtes SQLAlchemy) et modèles.
  • Une authentification par email et mot de passe : hachage bcrypt, jeton JWT signé en HS256 qui expire au bout de 60 minutes.
  • Des permissions par rôle vérifiées dans la couche services, indépendamment des menus affichés.
  • Les règles métier du cahier des charges : un événement n'existe que pour un contrat signé, le montant restant dû ne peut être ni négatif ni supérieur au total, un employé ne peut pas supprimer son propre compte.

Points techniques

  • Schéma PostgreSQL versionné avec des migrations Alembic.
  • Monitoring avec Sentry : les erreurs métier sont affichées à l'utilisateur, seules les erreurs inattendues remontent, sans données personnelles.
  • Tests unitaires, d'intégration et fonctionnels avec pytest et des factories de données de test.

Pour aller plus loin

  • Exposer la logique métier dans une API REST.
  • Lancer les tests automatiquement dans une intégration continue.

Python · SQLAlchemy 2 · PostgreSQL · Alembic · PyJWT · bcrypt · Sentry · Pytest

Projet OpenClassrooms

SoftDesk API — API REST sécurisée

L'API d'une application B2B de suivi de problèmes techniques : les utilisateurs créent des projets, y ajoutent des contributeurs, ouvrent des tickets (issues) et les commentent. 

POST  /api/token/access/
GET   /api/projects/
POST  /api/projects/{id}/contributors/
GET   /api/projects/{id}/issues/
POST  /api/projects/{id}/issues/{id}/comments/

Ce que j'ai construit

  • Une API REST avec Django REST Framework et des routes imbriquées : projets, puis tickets, puis commentaires.
  • Une authentification JWT (Simple JWT) : jeton d'accès de 30 minutes, jeton de rafraîchissement d'une journée.
  • Trois permissions sur mesure : seuls les contributeurs accèdent à un projet, seul l'auteur modifie ou supprime son contenu, seul l'auteur d'un projet gère ses contributeurs.

Points techniques

  • Un modèle utilisateur personnalisé pensé pour le RGPD : âge minimum de 15 ans, consentements explicites (être contacté, partager ses données), suppression du compte par l'utilisateur.
  • Des serializers distincts pour le profil public et le profil personnel : l'API n'expose jamais l'email ou l'âge d'un autre utilisateur.
  • Un ticket ne peut être assigné qu'à un contributeur du projet ; mots de passe en écriture seule et hachés ; identifiants UUID pour les commentaires ; pagination par 20.

Pour aller plus loin

  • Couvrir les permissions par une suite de tests automatisés.

Python · Django · Django REST Framework · Simple JWT · drf-nested-routers · SQLite

Projet OpenClassrooms · en production

Orange County Lettings — une application Django prête pour la production

Un site de locations immobilières livré sous la forme d'un seul projet Django : je l'ai refactorisé, couvert de tests, doté d'un monitoring, conteneurisé avec Docker et déployé par un pipeline automatisé.

  1. PushGitHub
  2. Flake8 + Pytestcouverture ≥ 80 %
  3. Docker Hubimage taguée par commit
  4. Renderdéploiement automatique

Ce que j'ai construit

  • Le découpage du projet monolithique en trois applications Django (lettings, profiles et le site principal), avec des pages d'erreur 404 et 500 personnalisées.
  • Des tests automatisés avec Pytest sur les modèles, les URL, les vues, les templates et les logs : 96 % de couverture, et un pipeline qui échoue sous 80 %. Vérification Flake8 à chaque push.
  • La journalisation Python et la remontée d'erreurs vers Sentry, configurées par variables d'environnement.
  • Une image Docker servie par Gunicorn, avec les fichiers statiques servis par WhiteNoise.

Points techniques

  • Pipeline GitHub Actions : lint et tests à chaque push et pull request ; sur master, l'image est publiée sur Docker Hub, taguée latest et avec le SHA du commit, puis déployée sur Render via un deploy hook.
  • Rien n'est publié ni déployé si le lint, les tests ou le seuil de couverture échouent.
  • Aucun secret dans le dépôt : secrets GitHub Actions et variables d'environnement Render, DEBUG désactivé en production.
  • Une documentation technique sur Read the Docs : installation, architecture, modèles de données, déploiement et CI/CD.

Pour aller plus loin

  • Passer à des versions maintenues de Django et de Python (le projet est parti de Django 3.0 et Python 3.9).
  • Remplacer SQLite par PostgreSQL en production.

Python · Django · Pytest · Flake8 · Sentry · Docker · Docker Hub · GitHub Actions · Gunicorn · WhiteNoise · Render · Read the Docs

LIT-Revu — application web Django

Une plateforme communautaire de critiques de livres et d'articles : on demande une critique en publiant un ticket, les autres membres y répondent, et chacun suit les personnes qui l'intéressent.

Ce que j'ai construit

  • Inscription et connexion ; création et modification de tickets (avec image) et de critiques, ou des deux en une seule étape.
  • Un système d'abonnements et un flux personnalisé qui mêle tickets et critiques des personnes suivies, triés par date.
  • Une recherche d'utilisateurs avec autocomplétion en JavaScript.

Points techniques

  • Contraintes d'unicité en base de données : une seule critique par utilisateur et par ticket, pas de double abonnement.
  • Requêtes du flux optimisées avec select_related pour éviter les requêtes N+1, et index sur la date de création.
  • Suppression du fichier image quand le ticket associé est supprimé.

Pour aller plus loin

  • Ajouter des tests automatisés sur le flux et les droits de modification.

Projet OpenClassrooms

AlgoInvest & Trade — optimisation sous contrainte

Trouver la meilleure combinaison d'actions à acheter avec un budget de 500 € : une variante du problème du sac à dos, sur 20 actions puis sur deux jeux de 1 000 actions.

Comparaison des deux algorithmes
Force brute Algorithme glouton
Complexité O(2ⁿ) O(n log n)
20 actions 1 048 576 combinaisons testées, 99,08 € de profit (optimal) 97,48 € de profit, en quelques millisecondes
1 000 actions Impossible : 2¹⁰⁰⁰ combinaisons Près de 198 € de profit sur chaque jeu de données

Ce que j'ai construit

  • Une force brute qui parcourt les 2²⁰ combinaisons à l'aide de masques binaires, pour obtenir la solution optimale de référence.
  • Un algorithme glouton qui trie les actions par rentabilité, puis les achète tant que le budget le permet.
  • Le nettoyage des données (prix nuls ou négatifs) et un rapport qui compare mes résultats à ceux de l'analyste.

Pour aller plus loin

  • Comparer le glouton à une solution exacte en programmation dynamique, pour mesurer l'écart à l'optimum.

Projet personnel · en production

API de contact — FastAPI en production

Le formulaire de contact de ce site s'appuie sur une API que j'ai développée et déployée : elle valide chaque message, puis me le transmet par email.

  1. Formulairece site
  2. API FastAPIapi.tommouquet.com
  3. Resendenvoi de l'email
  4. Ma boîte mailavec « répondre à »

Ce que j'ai construit

  • Un endpoint POST /contact en FastAPI, avec une validation Pydantic : email valide, longueurs minimales et maximales, espaces superflus retirés.
  • L'envoi asynchrone de l'email via l'API Resend, avec l'adresse de l'expéditeur en « répondre à ».
  • Un front statique séparé de l'API, avec une image Docker (Nginx) construite et vérifiée à chaque push.

Points techniques

  • Sécurité : contenu échappé avant insertion dans l'email HTML, retours à la ligne retirés de l'objet, CORS limité à mes domaines et à la méthode POST.
  • Configuration par variables d'environnement, avec un arrêt immédiat au démarrage si une clé manque, et un endpoint /health.
  • Pipeline GitHub Actions : tests Pytest et Playwright, build de l'image Docker, puis déploiement du site sur Render, seulement si tout passe.

Pour aller plus loin

  • Tester l'API elle-même avec le TestClient de FastAPI et un envoi d'email simulé.
  • Ajouter une protection anti-spam : champ piège et limitation du nombre de requêtes.

Python · FastAPI · Pydantic · Resend · Docker · Nginx · GitHub Actions · Playwright · Render
